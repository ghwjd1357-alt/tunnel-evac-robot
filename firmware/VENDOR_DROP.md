# firmware/ — Teensy 펌웨어 작업본 (2026-08-05 신설)

> **이 폴더는 무엇인가**: 구동부 파트가 만든 Teensy 펌웨어를, **역할 A 가 고쳐서 다시 구울 수
> 있도록** 저장소에 들여온 작업본이다. 빌드 환경 구성·필수 패치·재현성 기준점은
> `docs/FIRMWARE_REBUILD.md` 가 정본이다. 여기엔 **소스와 그 출처 증거**만 둔다.

## 0. 왜 저장소에 두나

Desktop 수령본에서 직접 고치면 세 가지를 잃는다.

1. **되돌릴 곳** — 안전 기능(`re-arm`)을 처음 만드는 작업이다. `git` 이 모든 변경을 기억해야
   망가뜨려도 한 줄로 복구된다.
2. **무엇을 바꿨는지의 증거** — `git diff` 가 "원본 대비 정확히 이 줄"을 보여준다.
   구동부에 변경을 전달할 때도 이 diff 가 그대로 근거가 된다.
3. **독립 검토** — `re-arm` 은 **안전 기능**이다. 저장소 밖에 있으면 `AGENTS.md §5` 의
   구현자 ≠ 승인자 절차 밖으로 샌다. 검토 라우팅 = `docs/TEST_GATES.md §7`.

⚠ `src/**` 동결과는 **무관**하다. 별개 최상위 폴더이므로 동결 예외를 쓰지 않는다.

## 1. 소유 경계 — 이걸 먼저 읽는다

| | 소유 |
|---|---|
| **펌웨어 원본 저작·유지** | **구동부 파트** (`AGENTS.md §1` 팀 경계) |
| 이 폴더의 사본과 역할 A 의 수정 | 역할 A |
| 로봇에 실제로 굽는 행위 | **사용자 승인 필요** (모터 전력 0V·바퀴 공중 전제) |

🔴 **역할 A 가 고쳤다고 그것이 구동부의 정본이 되지 않는다.** 수정본을 실차에 올릴 때는
diff 와 시험 결과를 구동부에 전달해 **양쪽 정본을 일치시킨다.** 두 벌이 갈라지면 다음
회신·재빌드에서 어느 쪽이 진짜인지 아무도 모르게 된다.

⚠ **폴더 이름을 바꾸지 않는다** — Arduino 는 폴더명과 `.ino` 파일명이 같아야 스케치로 인식한다.
줄여 부르고 싶어도 `teensy_integrated_base_v1_4` 그대로 둔다.

★ **이 폴더의 최초 커밋이 "원본 그대로"의 기준점이다.** 이후 어떤 수정을 해도
`git diff <최초커밋> -- firmware/` 로 원본 대비 전량 변경을 뽑을 수 있다.

⚠ **Desktop 수령본은 지우지 않는다.** 저장소 사본이 오염됐을 때의 독립 대조군이다.

빌드에는 라이브러리 5개가 필요한데 **117MB 라 저장소에 넣지 않았다.**

- 실물 위치: `~/Desktop/teensy_required_libraries_v1_4/`
- 버전·해시·전수 대조 기록: `docs/JETSON_SETUP.md §5-d`
- 설치·패치 절차: `docs/FIRMWARE_REBUILD.md §2`·`§3`

컴파일은 전부 통과하므로 코드 문제로 오인하기 쉽다. 새 PC 에서 처음 빌드하면 여기부터 본다.

## 5. 수정할 때 지키는 것

1. **한 번에 하나씩.** ①②③ 을 한 커밋에 섞지 않는다 — 문제가 나면 원인을 못 가른다.
2. **무변경 재빌드 기준점과 대조한다** (`docs/FIRMWARE_REBUILD.md §4`). FLASH·RAM 이 몇 백~몇 천
   바이트 늘면 정상, 급변하면 의도 밖의 것이 딸려 들어온 것이다.
3. **굽기 전에 `sha256sum -c` 로 무엇이 바뀌었는지 먼저 안다.** 원본 해시는 당연히 깨진다 —
   깨진 사실이 아니라 **`git diff` 의 내용**이 근거다.
4. **업로드는 모터 전력 0V·바퀴 공중에서만**, 그리고 사용자 승인 뒤에.
5. 굽고 나면 `/firmware/info` 를 **`--full-length` 로** 확인한다(기본 출력은 128자에서 잘린다).
