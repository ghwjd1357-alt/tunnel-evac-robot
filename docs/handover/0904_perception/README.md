### 위 표는 **프레임당 계산시간**이다 — 실제 발행률과 다르다

```
ros2 topic hz /detections           →  12.29 Hz  (표준편차 0.006)
ros2 topic hz /camera/debug_image   →  12.03 Hz
```

계산 환산 13.6 Hz 와 실측 발행 12.29 Hz 의 차이는 카메라 동기화(`ApproximateTimeSynchronizer`)
대기분이다. **대외적으로 인용할 숫자는 실측 발행률 12.29 Hz 다.**
기준선의 대응 실측치는 **3.7 Hz** 였다(표준편차 0.018).

## 4. 추적기 교체 — 정확도는 떨어지지 않았다

`bytetrack.jsonl` / `mytrack.jsonl` · 분석 = `scripts/analyze.py`

| | ByteTrack (원본) | CentroidTracker (직접 구현) |
|---|---|---|
| 프레임 | 265 | 314 |
| 사람 잡힌 프레임 | 230 (**87 %**) | 273 (**87 %**) |
| pose 처리시간 | 67.8 ms | **27.0 ms** |
| 고유 track_id | 3 | 5 |
| **최장 연속 추적** | 169 프레임 (64 %) | **273 프레임 (87 %)** |
| 판정 분포 | ok 162 / fallen 58 / unknown 10 | ok 208 / fallen 69 / unknown 15 |

**탐지율은 87 % 로 동일하고, ID 연속성은 오히려 좋아졌다.** ByteTrack 은 같은 사람을 169 프레임에서
놓치고 새 ID(`8`)를 발급했는데, 직접 구현은 273 프레임 내내 `id=1` 을 유지했다.

고유 ID 가 5개로 늘어난 것은 화면 가장자리에서 1~10 프레임짜리 조각이 생긴 것이고
(`id 2·4` 는 각 1 프레임), 주 트랙은 끊기지 않았다.

🟡 **한계**: 표본이 **한 사람 · 한 장면 · 실내**다. 다중 인원 교차나 가림(occlusion)에서는
ByteTrack 이 유리할 수 있다 — 그 조건은 **측정하지 않았다.**

## 5. 🔴 발견 — 디버그 화면 색 상수가 발행 인코딩과 어긋나 있었다

`perception_node.py` 는 박스 색을 **OpenCV 관례(BGR)** 로 적어놓고, 이미지는 **`rgb8` 로 발행**한다.
그래서 화면에 나오는 색이 의도와 다르다.

| 클래스 | 코드값 | 의도 | 실제 화면 |
|---|---|---|---|
| `fire` | `(0,0,255)` | 🔴 빨강 | **🔵 파랑** |
| `person_fallen` | `(0,165,255)` | 🟠 주황 | **🔵 하늘색** |
| `person_unknown` | `(0,255,255)` | 🟡 노랑 | **🩵 청록** |
| `person_ok` | `(0,255,0)` | 🟢 초록 | 🟢 초록 (대칭이라 우연히 일치) |

**초록만 멀쩡해서 오래 안 보였다.** `(0,255,0)` 은 뒤집어도 같은 값이다.
`perception_node_0904.py` 에서는 RGB 순서로 바로잡았다(`perception_0904.patch` 에 포함).

🔴 **시연 영향**: 고치지 않으면 **화재 박스가 빨강이 아니라 파랑으로 나온다.**

## 6. 🟠 미해결 — 흰 의자가 `smoke` 로 잡힌다

| 측정 | smoke 오탐 | 비율 |
|---|---|---|
| ByteTrack 검증 (원본 `.pt`) | 4 / 265 | 1.5 % |
| CentroidTracker 검증 (원본 `.pt`) | 5 / 314 | 1.6 % |
| **최종 (TensorRT)** | **13 / 713** | **1.8 %** |

대상은 **흰색 라운드 의자**이고 카메라가 **약 1.6 m** 로 가까워질 때 뜬다. 실시간 카메라에서도
같은 의자(및 검은 의자)에서 재현됐다. 신뢰도 **0.40 ~ 0.50**, `fire_conf` 임계값은 **0.38**.

**관제까지는 흘러가지 않는다** — `perception_adapter/adapter_node.py` 가 이중으로 막는다:
`trigger_class = 'fire'` (smoke 는 애초에 대상 아님) + `min_confidence = 0.60`.
즉 `/alarm` 은 나가지 않고 미션 상태도 안 바뀐다. **디버그 화면에만 그려진다.**

### 대응 후보와 그 한계

`fire_conf` 를 올리는 것이 가장 쉬우나 🔴 **0.50 으로는 부족하다** — 관측 최댓값이 정확히 0.50 이다.
자르려면 **0.55 이상**이어야 한다.

🔴 **그런데 이 값을 지금 확정하면 안 된다.** 우리는 **진짜 불이 몇 점으로 잡히는지 한 번도 재본 적이
없다.** 실제 화염이 0.5 대에 잡힌다면 임계값 상향은 **화재를 놓치는 쪽**으로 작동한다.
오탐 제거와 미탐 유발이 같은 손잡이에 달려 있고, 우리는 손잡이의 한쪽 끝만 측정한 상태다.

**전제조건부 처리**: 시연 촬영용으로만 `fire_conf:=0.55` 를 **실행 인자로** 준다(코드 수정 아님).
**재개방 조건 = 실제 화염(라이터·화재 영상 등)에 대한 신뢰도 분포를 실측하는 시점.**
그 측정 전까지 이 값은 "오탐이 해결됐다"가 아니라 **"실화재 점수를 아직 모른다"** 는 뜻이다.

## 8. 재현 방법

`scripts/` 의 파일은 **젯슨 `/tmp` 에 올려놓고 쓰는 것을 전제**로 한다.

```bash
scp scripts/*.py scripts/*.sh hanhan@jetson.local:/tmp/
scp perception_node_0904.py hanhan@jetson.local:/tmp/perftest/pn_FINAL.py
```

| 스크립트 | 용도 |
|---|---|
| `run_video.sh` | bag 재생 + 인지 + 프레임 덤프 → `/tmp/vidframes.tgz` |
| `run_live.sh` | 카메라 + 인지 + MJPEG 스트리머 (`bash /tmp/run_live.sh stop` 로 종료) |
| `mjpeg_server.py` | `/camera/debug_image` 를 브라우저로 (`http://<젯슨IP>:8081`) |
| `dump_frames.py` | `/camera/debug_image` → jpg 연번 |
| `analyze.py` | `*.jsonl` 의 track_id 연속성·판정 분포 |

### 🔴 밟기 쉬운 함정 3개 (전부 실제로 밟았다)

1. **`set -u` 를 ROS `setup.bash` 앞에 두면 죽는다** — `AMENT_TRACE_SETUP_FILES: unbound variable`.
2. **비대화형 ssh 는 `.bashrc` 를 안 읽는다** → `torch` 가 `libcudss.so.0` 을 못 찾는다.
   스크립트 안에서 직접 export 해야 한다:
   ```bash
   export LD_LIBRARY_PATH=/usr/local/cuda/targets/aarch64-linux/lib:/home/hanhan/cudss_lib${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}
   ```
   (= `0904_역할B_인지코드_검토.md §5` 의 P1-2 가 여기서도 그대로 재발한다)
3. **`cv_bridge` 는 `yolo_env` 안에서 못 쓴다** — numpy ABI 불일치로 `_ARRAY_API not found`.
   `np.frombuffer` + `reshape` 로 직접 풀고, **`rgb8` 이므로 `[:, :, ::-1]` 로 BGR 변환**해야 한다.
   이걸 빼먹어서 첫 산출 영상이 통째로 파랗게 나왔다.
