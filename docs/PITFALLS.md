> 세션 파괴급 5종 축약본은 `AGENTS.md §4` (매 세션 자동 적용). 여기는 전체 정본.

## 1. 프로세스/셸

- **`pkill/pgrep -f` 자기 매칭 자살** — 명령 문자열에 프로세스명이 들어가면 자기 셸 kill(2회 실측) → 브래킷 트릭 `pgrep -f "ros2[ ]launch"`. **`pkill -x` 는 comm 15자 잘림** — `robot_state_publisher`→`robot_state_pub`, `async_slam_toolbox_node`→`async_slam_tool` → 긴 이름은 `pkill -f "…[_]…"`. → 0705_현황 §10
- **`ros2 launch` 백그라운드 부모부터 kill** — 부모 생존 시 자식(planner·bt_navigator·gzserver) 좀비·중복 라이프사이클. **부모 kill -9 는 고아 nav2** → 좀비 bt_navigator 가 goal 가로챔(증상 매번 다름) → cleanup `pkill -9 -f "lib/nav2[_]"` 필수. → 0705_현황 §18
- 재시작 시 좀비 누적 + `TF_OLD_DATA` 폭주 → `pkill -9` 전부 + `ros2 daemon stop/start`. 백그라운드 런치는 수동 `setsid nohup` 불안정 → Claude 는 Bash `run_in_background`. → 0626_현황
- **셸 `set -u` 는 ROS setup.bash source 뒤에** (setup.bash 가 미정의 변수 참조 → 즉사). trap 은 `INT TERM` + `exit 130/143` (중단 후 계속 실행 봉쇄). → 0705_현황 §15.7
- **GNU `timeout N`은 TERM 무시 프로세스를 강제 종료하지 못함** — 실제 hard 상한은
  `timeout --kill-after=유예 N`처럼 SIGKILL 유예까지 있어야 한다. mission E2E의
  param/state/daemon뿐 아니라 `-w 1 topic pub`도 같은 helper를 써야 한다. → 0723_현황 §15.7
- `service call` 응답 파싱은 repr 형식 `success=True` (`success: True` 아님). → 0719_현황 §8
- 🔴 **Jetson 에서 `journalctl --list-boots` 로 재부팅을 탐지할 수 없다** — ① 부팅 항목이
  **1개만** 남는다(저널이 재부팅을 넘어 보존되지 않아 목록이 초기화된다) ② RTC 배터리가 없어
  부팅 직후 옛 시각으로 시작했다가 NTP 가 뛰어올리므로 **저널이 적은 부팅 시각과 `uptime -s`
  가 두 달씩 어긋난다**(2026-08-07 실측: 저널 `06-06`, `uptime -s` `08-07 15:33`).
  **시계와 무관한 두 가지를 쓴다** — 재부팅하면 값이 바뀌는 `/proc/sys/kernel/random/boot_id`
  와, 단조 증가하다 재부팅 시 작아지는 `/proc/uptime`. → 0807 실측
- 🔴 **여러 터미널을 열어 두면 Jetson 명령을 노트북에서 돌리게 된다** — `find /sys …`·
  `uptime -s` 같은 명령은 **양쪽에서 다 성공**해서 결과만 보고는 못 가른다(2026-08-07 에
  실제로 노트북 ACPI `BAT0` 경로를 Jetson 결과로 읽었다). 실차 진단 명령 앞에는
  **`echo "== HOST=$(hostname) ARCH=$(uname -m) =="`** 를 붙인다 — Jetson 은 `aarch64` 다.
- 🔴 **Teensy 4.1 보드 버튼은 reset 이 아니라 Program(부트로더) 진입이다.** 브레드보드
  작업 중 실수로 눌리면 보드가 **HalfKay 부트로더**로 올라와 **`/dev/ttyACM*` 이 아예 안 생긴다**
  — 시리얼이 아니라 HID 로 열거되기 때문이다. udev 규칙(`idProduct=="0483"`)도 매칭되지 않아
  `/dev/teensy_drive` 가 사라지고, agent 는 `Serial port not found … waiting for connection` 만
  반복한다. **배선·펌웨어 문제로 오진하기 쉽다.** → 0806 시공 실측
  ```bash
  lsusb | grep 16c0
  #  16c0:0478  Teensy Halfkay Bootloader  → 부트로더에 멈춤 (스케치 미실행)
  #  16c0:0483  Teensyduino Serial         → 정상 (스케치 실행 중)
  ```
  **복구 = 전원 재인가.** 스케치가 온전하면 `0483` 으로 복귀한다. 🔴 **`0478` 그대로면 그때는
  플래시가 비어 있는 것**이므로 재업로드다 — 두 경우가 이 한 번의 관찰로 갈린다.
- 🔴 **`arduino-cli board list` 는 Teensy 를 두 줄로 보여준다** — `/dev/ttyACM0`(serial, 이름
  `Unknown`) 과 `usb3/3-2`(teensy 프로토콜, 품번·FQBN 표시). **"ttyACM 줄에 Teensy 가 보여야
  한다"로 판정하면 정상 상태를 실패로 오판한다.** 업로드 포트는 후자를 쓴다(Program 버튼을
  눌러도 남는다). → 0806 시공 실측 · `FIRMWARE_REBUILD.md §5-a`

## 2. ROS 토픽·통신·테스트 자동화

- **`topic pub --once` 유실** — 디스커버리 매칭 전에 쏘고 죽음 → `-w 1 --times 2~3`. → 0705_현황 §14.3
- ★ **활성 런북의 `ros2 topic echo … --once` 는 전부 `timeout --kill-after=2s 10s` 로 감싼다**
  (08-04 검토 §39.3 P2-4). 발행자가 없거나 DDS 발견이 실패하면 `--once` 는 **영영 안 돌아온다**
  — 이 저장소가 **13분 27초 실측**으로 겪은 함정이다(`tools/d0_check.sh:103`).
  **전수 근거는 손으로 세지 말고** `grep -n "ros2 topic echo" docs/*.md | grep -v timeout` 출력을
  그대로 쓴다. ⚠ **상한을 안 거는 예외는 두 종류뿐**이며 그 밖은 결함이다:
  ① 사람이 화면을 보다가 `Ctrl+C` 하는 **관찰용 스트림**(`TEST_GATES §2` 의 `/mission_state`
  — `--once` 를 오히려 금지한다) ② **역사 서술 안의 옛 명령 인용**(`MASTER_PLAN §3`).
- ★ **`--symlink-install` 이라도 `data_files`(launch·config·urdf)는 `build/` 사본을 거친다**
  — `install/…/share/<pkg>/urdf/x.urdf` 는 `src` 가 아니라 `build/<pkg>/urdf/x.urdf` 를 가리킨다.
  즉 **`src` 의 URDF·YAML·launch 를 고쳐도 `colcon build` 없이는 실행에 반영되지 않는다**.
  파이썬 모듈만 src 로 직결된다. D+1 에 라이다 높이를 `robot_real.urdf` 에 넣을 때 정확히
  이 자리를 밟는다 — 고친 뒤 **반드시 `colcon build --symlink-install`** 을 다시 돌린다.
- 상태성 신호(/siren 등)는 전환 1회가 아니라 **매 tick 반복 발행** (늦은 구독자 대비).
- 자동화에선 명령 도달을 **상대 노드 로그로 수신 확인** 후 다음 단계. 스폰류 서비스는 멱등으로.
- **오래 뜬 액션 서버 + 새 CLI = goal 응답 유실 가능** (send_goal 영구 대기) → 타임아웃+1회 재전송. → 0705_현황 §15.7
- 테스트 가짜 시계는 **정수 ns 누적** (float 0.1×11=1.0999… 로 디바운스 경계 미달 가짜 실패).
- rosbridge 서비스 타입은 `rosapi_msgs/srv/…`. → 0718_관제시스템

## 3. 런치/setup.py

- 런치·월드 파일은 **`setup.py` `data_files` 등록 필수** (+`import os`, `from glob import glob`). → 0621_현황
- `parameters` 키는 `declare_parameter` 이름과 정확히 일치 / remap 은 발행·구독 양쪽 / `get_parameter().value` 의 `.value` 누락 시 객체 반환 에러.
- **시뮬 자작 노드 `use_sim_time:=true` 필수.** 정본 설정은 운영 기준 — 특수 세션(mapping 등)은 명시 오버레이로 (회귀에 없는 모드가 정책 변경의 사각지대). → 0719_현황 §14

## 5. URDF/diff_drive

- **belly drag** — 몸통 바닥이 지면에 닿으면 안 감 → 클리어런스(z=0.05). 바퀴 반경 교체 시(0.10→0.065) 차고 재조정 재발 주의.
- **4륜 강구동 = Gazebo 과구속** (제자리회전 불가) → 시뮬은 2구동휠+캐스터. 모든 link `<inertial>` 필수. 마찰은 `mu1/mu2`, `kp` 낮추면 파묻힘.
- **diff_drive `/odom` 은 spawn 위치 포함 world 좌표** (0,0 아님) → 목표 좌표는 `tf2_echo map base_footprint` 로 확인.
- ★ **`odometry_source` 기본 = world = 치트 오돔** (실위치 복사) — 오돔 실험·실차 근접 시뮬엔 `encoder` 명시. → 0705_현황 §10

## 6. Nav2

- map_server `yaml_filename not initialized` → nav2_params 에 `map_server: {yaml_filename: ""}` 섹션.
- **rolling global costmap + static layer 금지 (라이브 SLAM)** — 간헐 '성공+빈경로' ABORTED → `rolling_window: false` 가 표준. (구 "rolling:true 해결"은 폐기)
- DWB "No valid trajectories" → RPP 교체가 강건. RPP collision 오탐은 시뮬 한정 `use_collision_detection:false` (실차는 ON 복귀).
- **goal header.stamp = 0** (지금시각 찍으면 TF extrapolation → 회복스핀 무한). **콜백 블로킹 금지** (rclpy 싱글스레드 — server_is_ready 즉답+재시도 패턴).
- ★ **라이브 SLAM 중 goal 은 12m 이내 징검다리** (먼 goal = "off the global costmap" — localization 모드는 무관). → 0707_현황
- `inflation_radius ≥ 로봇 외접반경` (현 0.9). BackUp 은 Humble 기본 BT 의 RoundRobin 4번째 → 커스텀 BT 로 순서 당김(`bt_nav_to_pose_backup_first.xml`).
- 막힌 goal 은 BT 재시도 소진까지 ~2분 후 ABORTED — 무한 아님.

## 7. SLAM/EKF

- **TF 이중발행 금지** — EKF 켜면 diff_drive `publish_odom_tf:false`. Teensy 도 odom TF 발행 금지(실차 — EKF 단독).
- **EKF 엔 위치 말고 속도 융합** (odom0_config = vx·vy·vyaw). 시뮬 IMU 에 노이즈 부여 (covariance=0 이면 신뢰도 판단 불가).
- **`*_variance_penalty` 는 '분모'** — 키우면 벌점 약화! odom 신뢰 ↑ = 작게(0.02). ★ 긴 복도 드리프트 = 매처가 "안 움직였다" 선호 → `correlation_search_space_dimension` 축소 + 벌점 강화 + **회전도 잠가야 한 세트** (`angle_variance_penalty 0.05`·`minimum_angle_penalty 0.1`).
- **EKF 만으론 안 끝남** — SLAM 이 odom 을 덮어쓰므로 slam_params 튜닝까지 한 세트. 실차 시작값 = `slam_params_realodom.yaml` (penalty 0.02 는 실 odom 에 과신).
- **라이다 평면은 몸통 최상면보다 위** (자기타격 = 유령 상자 행렬 — 실물 동일, 하드웨어팀 전달). 낮은 장애물(콘 ~0.3m)은 라이다 사각 → Orbbec depth 필수의 실증 근거.
- 이동 중 gz vs tf2_echo 나이브 비교 = 샘플링 시차가 가짜 드리프트 — **정지 스냅샷만 신뢰.** → 0719_현황 §16

## 8. 미션노드 프로그래밍 (비동기 안전)

- **비동기는 '호출'이 아니라 '완결' 검증** — goal: 응답 수락 확인+stale 은 즉시 cancel+최종 CANCELED 관찰 / cancel: `goals_canceling` 확인 / 속도: `successful` 확인+재시도+**늦은 응답의 상태 덮어쓰기 가드**. "취소를 호출했다"≠"로봇이 멈췄다".
- **콜백 예외 방어** — `future.result()` 전파 시 goal_active 영구 대기 → try + FAULT 정리.
- **scan watchdog** — /scan 끊기면 visible/lost **판단 보류** (라이다 사망='추종 양호' 오독 방지). 복구 순간 디바운스 타이머 재무장 (단절 시간 산입 금지). `header.stamp` 단조성 확인.
- **외부 입력 신뢰경계** — /alarm: 유한값·frame=map·그래프 투영거리 상한. waypoints: validator (숫자·유한·부호·정수·상한·상호관계 — ★bool 은 int 하위 타입). 그래프 실패 시 직선 fallback 금지 → yaml 고정 집결지.
- ★ **플래그 하나가 두 뜻을 겸직하면 안전망이 조용히 죽는다** — `synced` 가 "한 번이라도 성공"으로 세팅되고 "지금 desired 가 반영됨"으로 읽혀, 값이 어긋난 채 종결돼도 아무도 복구를 안 했다. **원하는 값(desired)과 반영된 값(applied)은 따로 추적한다.** → `0720_현황.md §20.4`
- ★ **"안전 조치가 담당한다"고 적은 비차단 위험은 그 조치가 실제로 복구하는지까지 확인** — `_final_fail` 은 로그만 남겼고, 미뤄둔 위험이 다음 검토에서 P1 으로 돌아왔다. → `0720_현황.md §20.2`
- **비동기 요청엔 요청 단위 deadline** — '서비스 미준비'만 재면 "서비스는 떴는데 응답이 영영 안 옴"을 못 잡는다(로봇은 정지라 안전하지만 고장이 관제에서 은폐). 재시도가 예산을 연장하지 않게 무장은 1회. → `0720_현황.md §21.2`
- 단위테스트는 `MissionNode.__new__` 기법으로 rclpy 없이 콜백 직접 구동. → 0719_현황 §12~13
- ★ **"A 는 B 가 담당한다"고 범위를 나눌 땐 B 가 그 경로 전부를 덮는지 확인** — "guide 실패는 FAULT 가 담당"이 맞은 건 *진입* 실패뿐이었고, guide 성공 **후** stale 이 덮은 경우는 아무도 안 맡아 GUIDE 중 과속이 남았다. → `0720_현황.md §22.2`
- ★ **상태 판단은 그 상태를 소유한 쪽이 한다** — Manager 가 `_guide_confirmed` 로 노드 상태를 짐작하면 FAULT 자동복귀 같은 순간에 둘이 어긋난다. 콜백은 하나로 주고 분기는 state 소유자(MissionNode)가. → `0720_현황.md §22.4`
- **저속·모드 보장은 상태와 함께 자동 복귀하지 않는다** — FAULT 재시도로 GUIDE 에 돌아갈 때 controller 값은 그대로다. 복귀 시 다시 확인받을 것. → `0720_현황.md §22.4`
- ★★ **소비 지점 fail-closed 게이트라도 그 술어가 latch(과거)면 뚫린다** — "위험한 건 소비 지점에서 막자"(§23)로 위치는 옳게 옮겼는데, 게이트가 읽는 값이 `guide_confirmed`(과거 1회 성공)라 늦은 sync 가 실제 속도를 덮어도 True 로 남아 과속 goal 이 나갔다. **게이트 술어는 반드시 live(지금 실효값)여야 한다** — `guide_speed_applied` = `_applied == desired guide값`. public live 와 private latch 는 이름을 뚜렷이 분리(`guide_speed_applied` vs `_guide_was_confirmed`)해 다음 검토의 겸직 오독을 막는다. → `0720_현황.md §24.2`
- ★★ **실패 '결정'을 콜백 이벤트 한 번에만 맡기면 상태 전환 중 유실된다** — 저속 복구 소진(`_settle`)이 콜백(`_on_guide_speed_fail`)으로 딱 한 번 알리는데, 그 순간 상태가 GUIDE 가 아니라 SEARCH_BACK 이면 콜백 else(기본값)가 '늦은 통보'로 **무시** → GUIDE 복귀 후 live 게이트가 신규 goal 은 막아도 FAULT 없이 **고장 은폐 영구정지**. §24 와 같은 클래스(fail-open 기본값). 봉합 = 소비 지점(tick)에서 **매 tick live 술어**(`guide_speed_recovery_exhausted`)를 확인하는 fail-closed 가드 — 통보 유실과 무관하게 유도활성(GUIDE/SEARCH_BACK) 상태가 종결 실패를 한 tick 이상 못 이고 간다. 콜백은 즉시성, 가드는 backstop. **가드는 `ensure_sync` 앞**에 둔다(sync 요청 `_inflight` 이 술어를 가림). FAULT→SEARCH_BACK 재시도 복귀도 `request_guide` 재무장(안 하면 소진 술어 잔존→즉시 재-FAULT). → `0720_현황.md §25.2`
- ★★ **같은 안전 의무를 공유하는 상태는 신규 동작 소비 지점도 전부 게이트할 것** — GUIDE escape만 live 저속 게이트를 두고 SEARCH_BACK의 신규 goal은 `goal_active`만 봐, stale reconcile 중·FAULT 재무장 응답 대기 중 0.26으로 출발했다. “기존 goal은 reconcile 먼저” 정책과 “새 goal은 적용 확인 뒤” 정책을 분리한다: 기존 goal은 즉시 취소하지 않되 GUIDE·SEARCH_BACK 신규 `send_goal`은 모두 `guide_speed_applied`로 막는다. → `0720_현황.md §26.2`
- 껍데기 노드 테스트는 **매니저만 찌르지 말고 노드의 진짜 진입점(`on_cmd` 등)을 통과시킬 것** — 호출 누락·순서 뒤바뀜은 매니저 단위테스트가 못 잡는다. → `0720_현황.md §21.2`
- ★ **상태를 매니저로 옮길 때 동결 테스트가 그 노드 속성을 직접 만지면, 매니저 프로퍼티로 바꾸지 말고 노드에 평범한 속성으로 남긴 뒤 매니저가 콜백으로 미러**한다 — `goal_active` 를 `self.goals.active` 프로퍼티로 바꿨다면 이를 평범한 속성으로 세팅·독해하는 동결 하네스(N13~N20)와 `tick` 이 전부 깨진다. **`tick` 에는 새 매니저 참조를 한 줄도 넣지 않는 게 안전**(하네스가 매니저 미배선). 0-인자 호출 규약을 유지해야 하면 인자 대신 전이 속성(`_cancel_intent`)으로 의도를 넘긴다. → `0723_현황.md §4`

## 10. 전기계통 (08-04 신설 — 정본 = `docs/ELECTRICAL_BASELINE.md`)

- ★★ **퓨즈는 "평소 전류"가 아니라 "고장 시"로 고른다** — "코일은 0.16A 만 쓰니 얇은 선이어도 된다"고 넘어갔던 구간이, 실제로는 **부분 단락 20A 에서 메인 30A 퓨즈가 안 끊어지고 선만 녹는** 구간이었다. 소비 전류가 작다는 사실은 보호와 **무관**하다. 각 구간마다 "이 전선의 허용전류보다 작은 퓨즈가 앞에 있는가"를 따로 확인한다. → `ELECTRICAL_BASELINE.md §3-c`
- ★ **전선이 굵어지면 퓨즈를 추가하지 않아도 되는 경우가 있다** — 코일선을 18AWG(16A) 대신 **14AWG(32A)** 로 쓰면 30A 퓨즈 보호 범위 안에 들어온다. 부품 추가 0개. 단 **제품에 달려 나오는 하네스 선은 못 바꾸므로** 그 구간은 퓨즈로 해결해야 한다.
- ★ **안전장치 자체의 정격이 계통 퓨즈보다 낮으면 안전장치가 먼저 탄다** — E-stop 버튼 접점이 DC 3A 인데 앞 퓨즈가 30A 면, 회로 고장 시 **버튼이 먼저 소손**된다. 스위치·접점의 정격도 보호 대상이다.
- 🔴 **접점 단자가 3개면 Common 공유다** — `1NO+1NC` 인데 단자가 4개가 아니라 3개면 C 를 두 접점이 나눠 쓴다. **한쪽에 24V 를 걸면 다른 쪽에도 24V 가 나타난다.** 3.3V MCU 를 물리면 파괴된다. 단자 개수를 먼저 센다.
- 🔴 **5핀 릴레이의 `87a` 는 릴레이가 떨어질 때 살아난다** — 즉 **E-stop 을 누른 순간 87a 에 배터리 전압이 나타난다.** 미사용이라고 늘어뜨려 두면 누를 때마다 단락이 날 수 있다. 잘라내지 말고 **끝을 밀봉하고 고정**한다.
- 🔴 **E-stop 은 모터 가지만 끊는다. 로직·분배기·퓨즈는 살아 있다** — "E-stop 눌렀으니 안전하다"고 배선을 만지면 안 된다. 배선 작업은 **메인 스위치 OFF + 배터리 커넥터 분리** 후에만.
- 🔴 **`INPUT_PULLUP` 핀에 저항 분압을 걸면 내부 풀업과 싸운다** — 100k/15k 분압에 22kΩ 내부 풀업이 겹치면 약 1.3V 로 **LOW 도 HIGH 도 아닌 값**이 나온다. 접점(릴레이·스위치)으로 GND 에 직접 떨어뜨리는 편이 확실하고, 이때 **a접점(NO)을 쓰면 단선이 "정지"로 읽혀 fail-safe** 가 된다. → `ELECTRICAL_BASELINE.md §4-c`
- ★ **미연결 상태의 `INPUT_PULLUP` 핀은 "정상"을 발행한다** — 안 물려 두면 항상 HIGH 라, `ACTIVE_LOW=true` 펌웨어는 **눌러도 "정상"이라고 토픽을 내보낸다.** 배선이 없는 게 아니라 **거짓 정보를 적극적으로 발행**하는 상태다. 그 토픽을 소비하는 로직을 만들면 안 된다.
- 🔴 **릴레이 몸통의 `24V` 각인은 대개 접점이 아니라 코일 정격이다** — `40A / 24V` 를 보고
  "24V 를 40A 로 끊을 수 있다"고 읽으면 안 된다. 자동차 릴레이는 **코일 정격**을 몸통에 찍고
  접점 정격은 datasheet 에만 있다. **가르는 방법은 코일 저항 실측**이다: 측정한 저항으로
  소비전력을 내서 datasheet 의 코일 전력과 맞춰 보면 어느 코일 변종인지 확정된다
  (실측 322Ω → 24V 에서 1.79W = 사양 ≤1.8W 로 일치). 접점 표기는 코일 전압을 따라가
  **12V 코일 → 14VDC · 24V 코일 → 28VDC** 로 잡히고, 별도로 `Max. Switching Voltage`
  (이 계열은 75VDC)가 있다. → 0807 `ELECTRICAL_BASELINE.md §15`
- 🔴 **자동차 릴레이의 전류 정격은 연속 정격이 아닌 경우가 많다** — datasheet 에
  `Designed for intermittent load` · `Contact Load Rating … (1% duty cycle)` 이라고 적혀 있으면
  그 `40A`·`80A` 는 **간헐 정격**이다. 실사용이 정격의 1/4 이하면 여유가 크지만,
  **"정격이 40A 니까 40A 를 계속 흘려도 된다"로 읽으면 접점이 상한다.**
- ★ **DC 는 전류가 0 을 지나는 순간이 없어 아크가 스스로 안 꺼진다** — AC 정격(`250VAC 10A`)을 DC 에 그대로 쓰면 안 된다. 같은 접점이 DC 에서는 훨씬 낮은 값만 끊는다. **DC 정격이 명시된 부품**을 고른다.
- 🔴 **"접점을 직렬 2개로 두면 각 접점이 전압의 절반만 감당한다"는 틀렸다** — 직렬 2개를 두는
  이유가 **"하나가 융착돼도 나머지가 끊게"** 인데, **바로 그 단일고장에서 남은 접점 하나가
  전압 전부를 혼자 끊어야** 한다. 두 릴레이의 복귀시간도 어긋나 **먼저 열린 쪽이 아크를 혼자
  받는다.** 즉 반분 논거는 *안전장치가 필요한 순간에만 성립하지 않는다.* **각 접점이 단독으로
  전 전압을 끊는 정격**을 요구한다. 직렬 이중화는 **융착 대비**이지 전압 분담이 아니다.
  → `ELECTRICAL_BASELINE.md §13-a`(철회) · `§7-c`(검토 §53.1 P0)
- ★ **SSR(무접점 릴레이)은 고장 모드가 단락이다** — 망가지면 **항상 ON** 이 된다. 안전 차단의 마지막 층은 **눈으로 벌어진 틈을 확인할 수 있는 기계 접점**이어야 한다.
- ★ **"연속 통전형(continuous duty)"과 "시동 솔레노이드"는 겉모습이 같다** — 후자는 몇 초용이라 상시 통전하면 코일이 탄다. **코일 저항으로 판별**한다(24V 기준 16Ω 미만이면 의심). 자동차용 릴레이는 원래 연속형이라 이 함정이 없다.
- 🔴 **플라이백 다이오드를 거꾸로 달면 코일 통전 순간 배터리가 단락된다** — 줄무늬(캐소드)가 **코일 (+)** 쪽이다. 초보자가 가장 많이 틀리는 지점. 멀티미터 다이오드 모드로 방향을 먼저 확인한다.
- 🔴 **절연형 DCDC 를 쓰면 MCU–드라이버 GND 공유선이 유일한 기준점이 된다** — SD 시리즈는 입력 (−)와 출력 (−)가 끊겨 있다. 이 한 가닥이 빠지면 고장이 나는 게 아니라 **조용히 이상하게 동작**한다(PWM 무시·간헐 동작). 브레드보드에 꽂아 두면 안 된다.
- 🔴 **DCDC 입력 하한과 배터리 하한이 겹치면 로직 전체가 동시에 죽는다** — SD-50B-12/SD-15B-05 하한이 **19V** 이고 6S LiPo 는 셀당 3.17V 에서 19V 다. 저전압 알람을 **그보다 높게**(셀당 3.5V=21V) 잡아 먼저 경고가 나오게 한다.
- 🔴 **Teensy 4.1 은 외부 5V 와 USB 를 동시에 물리면 backfeed** — 바닥면 `VUSB`–`VIN` 절단이 선행이다. **자르면 USB 만으로는 안 켜지므로, 자르기 전에 5V 출력을 완성하고 전압을 먼저 측정**한다. 순서를 바꾸면 켤 방법이 없어진다.
- ★ **커넥터 안티스파크는 "연결"에만 듣는다** — XT90-S 의 프리차지 저항은 꽂을 때 돌입전류를 줄일 뿐, **부하 상태에서 뽑는 개폐**에는 아무 도움이 되지 않는다. 개폐용으로 쓰면 안 된다.
- **퓨즈는 배터리에 최대한 가깝게** — 퓨즈 **앞쪽** 전선은 어떤 것으로도 보호되지 않는다. 그 구간을 짧게 만드는 것이 유일한 대책이다. 퓨즈·스위치는 **(+) 한쪽에만** 넣는다(직렬 회로라 한쪽만 끊으면 멈춘다).
- 🔴 **LiPo 밸런스 커넥터에는 퓨즈가 없다** — 각 핀이 셀에 직접 연결돼 있고 간격이 2.54mm 다. 드라이버·핀셋이 스치면 **그 셀이 즉시 단락**된다(전원 계통 퓨즈는 이 경로를 안 지난다). 만지기 전에 금속 공구를 손에서 놓는다. 알람 소켓이 9핀(8S)이면 6S 는 두 칸이 남으므로 **`-` 표시 쪽 끝에 맞춰** 꽂는다 — 가운데에 꽂으면 셀 전압을 엉뚱하게 읽는다.
- 🔴 **로직 전원을 배터리로 옮기는 순간 `XT90 분리` 는 "리눅스 전원 뽑기"가 된다** — 그전까지
  XT90 은 마음대로 껐다 켜도 됐지만, Jetson 이 그 아래로 들어오면 **파일시스템이 손상**된다.
  몇 번은 멀쩡하다가 어느 날 부팅이 안 되고, 그때 udev 규칙 같은 것도 같이 사라진다.
  **종료 절차 맨 앞에 `sudo shutdown -h now` + 완전 종료 확인을 넣는다.** → 0806 시공 실측
- 🔴 **로직 전원을 옮기면 부팅 경주가 생긴다** — XT90 을 올리면 Teensy(약 5초)가
  Jetson(30초+)보다 먼저 깬다. 펌웨어는 `set_microros_transports()` 뒤 **`delay(2000)`** 만 주고
  `rclc_support_init` 을 부르므로 **반드시 실패**하고, **재연결 로직이 없어 `errorLoop()` 에서
  영구히 멈춘다.** 증상은 "장치는 보이는데 토픽이 `rosout`·`parameter_events` 뿐". 배선을 뜯게
  되는 자리다. **순서 = `XT90 → Jetson 부팅 → agent 기동 → Teensy 전원만 재인가`.**
  → 0806 시공 실측
- 🔴 **`errorLoop()` 는 두 원인을 같은 증상으로 보여준다** — `initializeImu()` 실패(BNO055 무응답)와
  `rclc_support_init` 실패(agent 없음)가 **둘 다 LED 100ms 점멸 + 토픽 0개**다. IMU 는
  micro-ROS 보다 **먼저** 초기화되므로, IMU 4가닥(`18`·`19`·`3.3V`·`GND`) 중 하나만 빠져도
  **노드 자체가 안 뜬다.** 먼저 "agent 먼저 띄우고 보드만 재부팅"으로 순서 원인을 지운 뒤
  IMU 배선을 본다. → 0806 시공 실측
- 🔴 **DCDC 는 입력과 출력의 전선 굵기 기준이 다르다** — 입력측은 위쪽 보호가 **메인 퓨즈뿐**
  이라 그 퓨즈가 끊길 때까지 버텨야 한다(30A → 14AWG). 출력측은 **DCDC 자체가 전류를 제한**
  하므로(15W/5V ≈ 3A) 얇아도 된다. 같은 계통이라고 같은 굵기를 쓰면 한쪽이 과잉이고
  한쪽이 위험하다.
- 🔴 **브레드보드 상태에서는 PWM/DIR 이 빠지는 것이 "안 도는" 고장이 아니라 "돌 수도 있는" 고장이다**
  — 입력이 부동(floating)이 되면 노이즈로 모터가 움직일 수 있다. 진동으로 접점이 빠지는
  브레드보드에서는 **가동 전마다 위험 배선(GND 공유선·PWM 4·DIR 4)만이라도 확인**한다.
  엔코더·IMU 는 안 보이면 바로 티가 나므로 소프트웨어(`/odom`·`/imu/data`)로 대신 본다.
- 🔴 **그 함정이 2026-08-07 에 실제로 터졌다 — 그리고 눈으로 보는 확인은 못 잡았다.**
  좌전륜 DIR 핀 하나가 빠져 **그 바퀴만 반대로 돌았고**, `#11` 시험 발행 도중에야 발견됐다.
  DIR 이 뜨면 드라이버가 LOW 로 읽어 **역회전**한다(PWM 이 빠졌으면 아예 안 돌아 금방 안다).
  → **배선 육안 점검으로는 부족하다. 통전할 때마다 바퀴를 공중에 띄운 채 짧게 돌려
  네 바퀴가 같은 방향인지 본다**(`JETSON_SETUP.md §7-c` 주행 허용 전제).
  🔴 **`d0_check` 검사 6(전진 부호)은 이걸 검사하지 않는다** — 바퀴를 **손으로 굴려**
  엔코더 부호를 보는 항목이라 모터 구동 방향과 무관하다. D+0 검사 8개 어디에도 없던
  구멍이었다. 근본 해결은 기판 제작이다. → 0807 실측
- ★ **과방전 방지 알람이 과방전을 일으킨다** — 저전압 알람 자체가 수 mA 를 상시 소비한다. 사용 중에는 무시해도 되지만 **1주 이상 꽂아둔 채 방치하면 그 소비로 배터리가 내려간다.** 장기 보관 시엔 뽑고 셀당 3.8V 근처(6S=22.8V)로 맞춰 둔다. **보호 장치의 대기 소비가 보호 대상을 깎는 구조인지 항상 확인**한다.
- ★ **저전압 임계값은 배터리가 아니라 부하 쪽 하한이 정한다** — LiPo 손상은 셀당 3.0V 아래지만, DCDC 입력 하한 19V(6S 기준 셀당 3.17V)를 지나면 **Jetson·Teensy 가 동시에 죽는다.** 그래서 3.5V(21V)로 잡아 19V 도달 전 여유를 만든다. **"부품이 견디는 값"이 아니라 "계통이 먼저 무너지는 값"에서 경보한다.**
- **하네스 선 색깔에는 규격이 없다** — 릴레이 소켓 배선 색은 제조사마다 다르다. **소켓 몸통에 새겨진 핀 번호**(30/85/86/87/87a)로 판단하고, 안 보이면 멀티미터 연속성으로 찍는다. 단자 각인도 못 믿으면 접점 동작을 직접 잰다.

## 11. 실차 구동부·펌웨어 (08-07 신설 — 정본 = `docs/REAL_ROBOT_VALUES.md §1`)

- 🔴 **엔코더 부호가 뒤집히면 오도메트리만 틀리는 것이 아니라 그 바퀴가 전속으로 달린다**
  (2026-08-11 R1 실측 신설). PI 는 `measuredAlongCommand = direction × filteredWheelVelocity`
  로 오차를 만드는데, 부호가 반대면 `error = target − (−v) = target + v` 라 **속도가 붙을수록
  오차가 커진다.** 적분기가 감겨 그 바퀴만 PWM 천장까지 간다 — 🔴 **명령 상한
  `MAX_LINEAR_CMD = 0.12` 는 *명령* 클램프이지 *출력* 클램프가 아니므로 실제 속도를 못 막는다.**
  → 부호 오류를 "지도가 좀 틀어지는 문제"로 분류하지 않는다. **속도 상한이 뚫리는 안전 문제**다.
- 🔴 **`d0_check` 검사 6 은 부호를 보지만 그 부호가 *어느 쪽 바퀴로 계산되는지*는 안 본다.**
  2026-08-11 R1 에서 좌전륜 엔코더가 **우측 바퀴처럼** 적분됐다. 펌웨어가
  `deltaLeft = 0.5×(dFL + dRL)` 로 좌측을 평균하므로 **FL 이 RL 을 지워 `deltaLeft = 0`** 이
  되고, 그 결과 **거리는 절반 · 없던 회전이 생긴다**(5초 직진에 `69.5°`). 눈으로는 로봇이
  똑바로 가므로 **육안으로는 절대 안 잡힌다** — 네 바퀴가 지면에 묶여 있어 빠른 바퀴는
  미끄러질 뿐이다.
  → **가르는 법**: 바퀴를 띄우고 **무장 해제**한 뒤 `ros2 bag record /odom` 을 켜고
  **한 번에 한 바퀴씩** 전진 방향으로 굴리며 **사이에 3초 이상 정지**한다. 구간별
  `Δyaw` 부호가 판정이다 — **좌측 2개는 음수, 우측 2개는 양수**여야 한다. 한 바퀴만 굴리면
  `Δyaw = ±0.5 × d / WHEEL_BASE` 라 부호가 그대로 드러난다.
  → 브레드보드라 **통전할 때마다** 의심한다. 08-07 DIR 핀 이탈과 같은 계열이고, 그때는
  통과했던 항목이라 **전기 시공 중의 회귀**로 본다.

- 🔴 **바퀴를 공중에 띄우면 명령보다 빠르게 돈다 — "가벼운 조건"이 아니라 "다른 조건"이다.**
  2026-08-07 실측: `linear.x = 0.05` 를 보냈는데 `/odom.twist.x` 가 **약 0.10**(2배)으로
  나왔다. 펌웨어 PI 가 `MIN_RUNNING_PWM` 바닥에 걸려 **더 못 줄이는** 것으로 보인다(무부하라
  최소 PWM 으로도 목표를 넘는다). ⚠ **오도메트리 스케일이 2배 틀린 경우와 이 데이터만으로는
  구분되지 않는다** — 가르는 것은 **R2(3m ±3%)** 다.
  → **공중 시험 기록에 "`0.05 m/s` 에서"라고 적을 때 그 값이 명령값인지 실측값인지 구분**한다.
- 🔴 **watchdog 은 계약 시각에 *발동*할 뿐 그 시각에 *정지*하지 않는다** —
  `WATCHDOG_TIMEOUT_MS = 500` 은 "500ms 에 정지를 시작한다"는 뜻이라, 실제 마지막 회전은
  항상 `500ms + 전송지연 + 기계관성` 이다(실측 초과분 19.9~37.1ms). **"N ms 안에 멈춘다"를
  완료판정으로 쓰면 어떤 정상 시스템도 통과하지 못한다.** → `JETSON_SETUP §7-c-0`
